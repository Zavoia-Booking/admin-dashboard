# Editing the items on an existing appointment

Implementation plan · 23 November 2026 · Covers the admin API, dashboard, and the existing customer app and website readers.

**Acceptance goal.** An owner can open an upcoming appointment, replace its bundle or change its services, save once, and reopen the same appointment with the revised items, price and end time. An assigned team member can do the same when “Allow reschedule without approval” is on. The appointment keeps its ID, customer and booking source. Drag-and-drop continues to move or reassign the booking as a whole.

## What the audit established

Creation already writes three appointment shapes. One service has a service reference. One bundle has a bundle reference and a record of its components. Several consecutive items with the same professional occupy one row with an ordered item list. A change of professional at creation starts a separate appointment. Both admin and marketplace creation use the same aggregation logic. Today the update request can express only a single replacement service, and the API explicitly refuses that field on bundle and multi-item bookings. [Creation and grouping](../../../admin-api/src/modules/appointment/appointment.controller.ts#L572) · [Shared aggregation](../../../admin-api/src/modules/appointment/run-grouping.ts#L83) · [Update request](../../../admin-api/src/modules/appointment/dto/update-appointment.dto.ts#L12) · [Current refusals](../../../admin-api/src/modules/appointment/appointment.controller.ts#L1030)

The November 20 repair stopped a partially saved change that combined a new service and price with the old bundle's identity and components. The November 22 browser run verified the temporary read-only editor. On November 23 a read-only local count found 433 upcoming single-service appointments, 5 bundles and 7 multi-item appointments, all with one assigned professional. Local appointment **#1805** contains service, bundle, service, service in that order. The dashboard's create selection handlers rebuild services and bundles in separate groups. Applying those handlers to this existing booking would move its second item. ## Rules for the implementation

| Area | Rule |
| --- | --- |
| Who and when | Owners can edit future pending or confirmed appointments in their business. Team members need the existing setting, access to the location, and assignment to that appointment. They can assign only themselves. Keep the existing owner-only location rule and the current location in the Edit form. Item changes lock at the start, including a different item of exactly the same length. The existing notes, confirmation, cancellation and status paths keep their own rules. |
| Unit of work | Edit the selected appointment and its one effective professional. Add, remove, or replace a whole service or bundle. At least one item must remain. A bundle's components are edited in the catalogue. Appointments for other professionals in the visit have their own IDs and times. |
| Retained items | Keep the recorded name, description, amount in minor units, duration, identifiers and bundle components. Keep their relative order and recalculate their start offsets. Catalogue price changes, a changed bundle definition, and a different professional do not reprice retained items. |
| New items | Offer services and bundles enabled at the appointment's location and belonging to its business. Validate the effective professional against the **resulting** contents. A new service uses the professional override, then the location override, then the service default, independently for duration and price. A new bundle uses its component default durations and its configured sum, fixed or discounted price. Keep the appointment currency and existing price display. |
| Customers and reporting | The agreed rule for an items-only change is to refresh the existing pending reminder. Immediate customer reschedule messaging follows an actual start-time change. The agreed completion-report rule is to use the revised, recorded items and total for an eligible marketplace appointment. Retained prices still reflect what the customer booked. The customer terms describe additional purchases as agreed with the business. |
| Team notifications | A genuine content change by an eligible team member creates one existing service-change notification for the owner. Changing time and contents in one save creates both existing owner notifications, each opening the same appointment. Owner edits, notes-only changes and unchanged selections produce no team-member service-change entry. |

## Implementation sequence

### 1. Extend the existing edit request

Add an optional ordered `items` list to `PUT /appointments/:id`. Keep the existing `serviceId` path and its guards for older clients and ordinary single-service replacements. Use the item list when editing a bundle, adding or removing services, or changing booking shape. The same request may include allowed changes to time, professional or notes.

Each entry either retains a line from the booking the editor opened, adds a service, or adds a bundle. For example, `[{"bookedIndex":0},{"bundleId":7}]` retains the original first line, puts the selected bundle second, and drops the other original lines. Positions distinguish existing occurrences of the same catalogue item without adding database IDs. Reject an empty list, conflicting instructions, repeated or out-of-range retained positions, and simultaneous `items` and scalar `serviceId`. Accept IDs and retained positions from the client. Calculate authoritative prices, durations, snapshots and permissions on the server.

For a list edit, carry the original appointment's existing `updatedAt` as an edit precondition. Validate it on the locked row. A stale editor gets a refresh-and-review response, including when two bundles have the same duration. Use a distinct stale-edit response so the current automatic schedule retry cannot reinterpret an index against a different list. The tradeoff is that a concurrent notes edit can also require reopening an item edit. Time-only, staff-only, notes-only and drag requests continue with their existing contracts. ### 2. Build the revised booking from existing code

Read retained entries from the server's original ordered snapshots. For a standalone service or bundle, use its saved row values, references and bundle breakdown. Follow the existing item reader for the three shapes. Use the raw saved fields where the display representation omits an identifier or changes a nested field name. Retained historical items can survive a disabled listing or a deleted catalogue link. When reducing a booking to one retained item, only attach a live reference if it still exists. For additions, share the service and bundle resolution already used by admin group creation. Extract only the overlapping block if needed. Check both the location offering and the professional's qualification. A professional can perform every component of a bundle even when the venue has disabled the bundle itself. For retained bundles, use the recorded components for qualification, with the existing current-bundle fallback for older rows missing that breakdown. Validate the final list so a removed service cannot disqualify a replacement professional. ### 3. Validate and save through the normal update transaction

Include actual item changes in both the controller's and the writer's scheduling checks, even when the duration stays the same. At present those checks recognize the scalar service field. Enforce the team permission on the server and lock the form controls consistently on screen. Use the existing business, venue timezone, working hours, midnight boundary, block checks and professional schedule rules over the **entire revised interval**. Exclude only the appointment being edited. The current edit rules allow a future change inside a creation-only minimum notice window. Keep the same-business buffer, and the actual-overlap check across businesses for a shared professional.

Use `updateWithPrevious`, its appointment-row lock, staff locks and final overlap check. Check the saved version, current time/status and team assignment under the lock before writing. A confirmed hours or calendar-block override still goes through the final staff conflict check. An invalid selection or a refused save leaves the original booking intact. An unchanged list should use the ordinary path for any other fields and produce no content side effects. Keep the existing post-commit availability refresh for old and new capacity. ### 4. Adapt the existing Edit form and slot search

Populate Edit from appointment details with one draft row per booked item and one professional for the appointment. Reuse the existing service and bundle sheets, booked-item rendering, price formatting, venue date controls, English/Romanian copy conventions and mobile layout. Retain rows in place, replace at the selected position, remove by occurrence, and append additions. Reopening or applying a picker without changing the selection must preserve the entire booking. A cleared draft can be edited further, with Save disabled until it contains an item. Keep “Select service” working for ordinary service replacements.

Compute the preview from booked values for retained lines and existing effective-value helpers for additions. Send the **combined duration**, professional and `rescheduleAppointmentId` through the existing single-professional slot lookup. The general catalogue `items` query would recalculate retained durations. Let the existing selected slot stand when the revised interval fits. Recheck if the draft changes while slots are loading. The API independently resolves the final values on save. Offer professionals who can perform every item in the revised list. If the known assignments have no eligible professional in common, ask the owner to change the selection. Use the established server-check fallback when historical catalogue details are missing. A team member sees only themselves. Preserve existing staff-less and multi-assignee read/move/notes flows. A list edit needs one explicitly selected professional if the legacy booking has no unique assignee. ### 5. Connect existing notifications and readers

Derive a genuine content change from the ordered booked items before and after the save. The current owner-notification check compares only scalar service IDs, so two different bundles can both look like a null service. Keep the stored before/after values independent, and compare ordered contents rather than the shortened calendar title alone. Use the existing notification kind, previous and revised booked names, translations and appointment link. Use the existing time-change and reassignment branches independently. Update the pending reminder snapshot once on an items-only edit. If the start changes, use the normal reschedule path with the revised booking and its end-of-day scheduling. ### 6. Verify through the actual save paths and release API first

Use disposable copies of representative bookings on the local stack. Record the original ID/UUID, references, snapshots, time, total, reminders and relevant notification counts. Drive the dashboard through Playwright, reopen the appointment via a fresh GET, and compare persisted fields. Use the API directly for validation cases the form prevents. Exercise the legacy scalar request on a bundle, a mixed or empty item request, a repeated retained position, and a newly added offering disabled at the venue. Confirm each refusal leaves the stored row and notifications untouched. Use the local recording provider for notification checks.
